# Wiping OpenWhispr's local data when a device is offboarded

When someone leaves, IT can remove what the OpenWhispr desktop app stored on their laptop: from inside the app with a device policy key, or with a script while the app is closed.

## Device policy keys

Both keys sit next to the other OpenWhispr device keys (macOS managed preferences for `com.gizmolabs.openwhispr`, `HKLM\SOFTWARE\Policies\OpenWhispr` on Windows, `/etc/openwhispr/device.json` on Linux).

| Key                           | Type                     | Effect                                                                                                                                                                                                                           |
| ----------------------------- | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `WipeLocalDataOnLaunch`       | string                   | A token of your choice. The first time the app launches and sees a token it hasn't acted on, it wipes the local data, records the token, and restarts as a fresh install. It wipes again only when you deploy a different token. |
| `WipeLocalDataIncludesModels` | boolean, default `false` | Also deletes downloaded speech and language models. Without it they stay, so a reassigned device doesn't download them again. On its own, without a token, it applies to the wipe a workspace removal starts.                    |

On Windows, `WipeLocalDataOnLaunch` is a `REG_SZ` and `WipeLocalDataIncludesModels` a `REG_DWORD` (0 or 1). On macOS, deploy them in a configuration profile: the app reads only managed values, so `defaults write` has no effect. On Linux, `/etc/openwhispr` and `device.json` must be owned by root and writable by no one else, or the app treats the device policy as invalid, and an invalid one never wipes.

Give each key the type shown. A value of another type, such as `<string>true</string>` in a profile, a `REG_SZ` `1` for `WipeLocalDataIncludesModels`, or a number as the token, makes the whole device policy invalid: OpenWhispr then says so and can't be used until it's corrected.

Deploy `WipeLocalDataOnLaunch` only to the devices you are offboarding: any device that hasn't acted on the token wipes at its next launch. On a device several people use, a token set for the whole device (in `HKLM`, `/etc/openwhispr`, or a device-level macOS profile) wipes the data of everyone there who opens OpenWhispr, not only the person leaving; a user-level macOS profile reaches only its user, and elsewhere use a script with the profiles or homes you name. The app reads the token only when it starts, so one already running (in the tray, or opened at login) wipes the next time it starts. A version released before these keys ignores them: a device still on one isn't wiped, and once it updates, it wipes at its next launch, whoever uses it by then. Before you hand a device on, check its audit log for the `local-data.wiped` line (below).

The wipe runs only when the app reads a valid device policy. A policy that can't be read, or that this version rejects, never triggers it. A plain sign-out never wipes.

If something can't be deleted (a file another program holds open, a note or temp folder the app can't read), or the app can't record the wipe in its data folder, OpenWhispr doesn't open. It says it couldn't remove all of its data, lists what stayed, records the attempt with `reason: "incomplete"`, and tries the whole wipe again at every launch until nothing is left. Once the attempt is on record, that holds even if you remove the token or the policy can't be read meanwhile, and each try takes the models and keeps the `AuditLogPath` the first one did, unless you deploy a new token. The token counts as acted on, and a removal's notice shows, only then. A folder or file the wipe removes whole, such as the recordings folder (`audio`), that the user replaced with a link to another place is reported the same way: the link goes, but what it leads to stays for you to delete by hand, and the next try finishes.

### What is removed

- The local database: notes, transcripts, history, dictionary, chats.
- Recordings and temporary audio files.
- Saved API keys and credentials, the sign-in token, and, in the production app, the keychain key that encrypted them (staging and dev builds share that key, so they leave it).
- Settings, browser storage (localStorage, cookies, caches), connector logins and skills.
- The Markdown copies of notes. In a folder the user chose, only the files the app's database records OpenWhispr writing there, and that still hold what it wrote, are deleted, along with the folders it made there and the ones that leaves empty, while nothing else is in them; the folder itself, a file edited or replaced by a link since, and everything else in it stay. A file the app can't reach or read, a notes folder that itself now leads elsewhere through a link, or a database it can't read, leaves the wipe incomplete, and the app keeps its database until it finishes, so the next try can still tell which files are its own. A folder inside a notes folder that the user replaced with a link (say, after moving it elsewhere) is reported too, but what the link leads to isn't followed, and the database still goes: delete the notes OpenWhispr wrote there by hand. As for a drive that isn't connected, only the dialog the user sees names the folder, and the next try finishes. A damaged database keeps the wipe from ever finishing; then delete the user's OpenWhispr data folder by hand, along with the note files OpenWhispr wrote in their notes folder. A notes folder on a drive or share that isn't connected (a Windows drive letter or share that can't be reached, or a drive missing under `/Volumes`, `/media`, `/run/media`, `/mnt` or `/run/user`) is reported, and that try counts as incomplete, but the database still goes, since keeping it would keep every note: delete the notes OpenWhispr wrote there by hand. Only the dialog the user sees names the folder, so ask them which one it was. The next launch's try then finishes. (A drive mounted anywhere else, such as a custom `fstab` path or a Windows volume mounted in a folder, can't be told from a deleted folder, nor can a notes folder at the root of a mount point that stays behind empty while its drive is away, so neither is reported.)
- The local search index, logs, and runtime downloads (GPU packs, llama.cpp, yt-dlp).
- Downloaded models, only with `WipeLocalDataIncludesModels`.

### What stays

- The audit log: the `audit` folder, or the audit files (`meeting-audit-<user>-<date>.jsonl`) in your `AuditLogPath`, and its crash marker. An `AuditLogPath` inside a folder the wipe empties keeps only those files; everything else in that folder still goes. The wipe is recorded there as `local-data.wiped`, with `trigger: "device-policy"`, `"workspace-removal"` or, for the scripts below, `"script"`; `reason: "incomplete"` means some file could not be deleted. A line that can't be written, or that a network `AuditLogPath` doesn't take within 5 seconds, is written at a later launch, with the time of the wipe.
- `local-data-wipe.json`, the last token acted on. Don't edit, remove or lock it. Removed, it lets the token wipe again. Damaged, it counts the deployed token as acted on, which also ends the retries of a wipe that didn't finish; while the app can't read it at all, every token you deploy later counts as acted on too. Run a script on such a device.
- On macOS, the Globe key's crash marker, which the next launch needs to put the user's Globe key setting back.

The app can't revoke tokens at Google, Microsoft or connector providers during the wipe; it deletes its local copies. Revoke the account at your identity provider as part of offboarding.

## Removal from the workspace

When an admin removes someone from a workspace with a policy (one at a time or in bulk) and leaves **Wipe OpenWhispr data on their devices** ticked, or your identity provider deprovisions them through directory sync, each device that workspace managed for them wipes the same data at its next policy check, even if another workspace still manages them. Only a device signed in to that account hears of the removal: one signed out of it, or signed in to another account, doesn't until it signs in to that account again, so offboard those with `WipeLocalDataOnLaunch` or a script. Nor does a device that never checks the workspace policy: one with `RequireSignIn` set to false, which keeps it to local processing, or with an invalid device policy. A device needs one policy check on this version before the removal to know which workspaces manage it. It then opens as a fresh install and shows "Your organization removed this device's OpenWhispr data." The audit log records it with `trigger: "workspace-removal"`.

Nothing is wiped when the admin unticks the box, when a member leaves the workspace on their own, signs out, or their session expires, when the directory moves an account to a new email address, or on a device that workspace never managed. A member who rejoins before a device checks in keeps that device's data. A device keeps downloaded models unless it also has `WipeLocalDataIncludesModels`, which works here without a token.

## Scripts (app closed)

Both scripts remove the in-app wipe's files for every user on the device, or only for the homes or profiles you name. The macOS script first quits OpenWhispr for the user whose home it cleans, never another user's; the Windows script skips a signed-in user's profile (see below), so OpenWhispr can't be running in one it cleans. They keep the `audit` folder, `local-data-wipe.json` and the Globe key marker too, and, as the app does, the audit files of an `AuditLogPath` inside the app's data folder. Each records its wipe in the user's audit log with `trigger: "script"`, in your `AuditLogPath` or else the kept `audit` folder: the macOS script writes it as the home's owner, so a home whose account no longer exists gets no line, and the Windows script uses `AuditLogPath` only while no one is signed in, and only when that folder already exists with no junction or link on its way (it never creates it). A Windows profile whose account no longer exists still gets a line, with `deviceUser: "unknown"`. Since they run as root or SYSTEM, they never follow a symbolic link or junction out of a user's home. A folder or file they remove whole that the user replaced with a link is reported as the app reports it: the link goes, what it led to stays for you to delete by hand, and the run fails, so the next one passes.

They also clean a Markdown notes folder inside that home or profile as the app does, from the app's database (on Windows through the SQLite built into Windows 10 and 11). A note file they can't read or remove, a database they can't read, or a notes folder that now leads elsewhere, fails the run and keeps the database, so a second run can still tell which files are the app's; a damaged database fails every run, so delete that user's OpenWhispr data folder (`~/Library/Application Support/open-whispr`, or `%APPDATA%\open-whispr` on Windows) by hand, along with the note files OpenWhispr wrote. A notes folder outside the home or profile is reported and fails the run, but isn't touched, since run as root or SYSTEM they never leave the home or profile, not even to look: delete the notes OpenWhispr wrote there by hand. The database still goes, so a second run passes. The same goes for a folder inside a notes folder that a link or junction now stands in for (reported as "it is reached through a link", or "through a junction or link" on Windows), which they don't go through. A notes folder that itself now leads elsewhere ("it now leads elsewhere") keeps the database: delete the notes behind it by hand and remove the link, and the next run passes. A database over 4 GB, a sparse one on Windows, or (on macOS) a record of more than 50,000 entries, counts as a damaged one: every run fails and keeps it, so use `WipeLocalDataOnLaunch` there, which has no such limit, or delete that user's OpenWhispr data folder by hand. Notes taking more than 4 GiB together stop the macOS script removing that home's notes partway (the rest of the run goes on): the database stays and the run fails. The next run goes on from there, since the notes removed no longer count, but the ones it keeps (edited ones, say) count every time, so kept notes that take more than 4 GiB fail every run.

Before removing anything in a home or profile that has OpenWhispr data, they mark it with `local-data-wipe.pending`: if the run is cut short or can't finish, and the user opens OpenWhispr before a second run, the app finishes the wipe before it opens and records it with `trigger: "script"`. That wipe removes models only when `WipeLocalDataIncludesModels` is set, so run the script again to remove them. A run killed outright (`kill -9`, a power cut, the MDM tool's timeout) while it reads a user's database can also leave a copy of it, which the next run deletes: in `/tmp/openwhispr-wipe.*` on macOS, which only root and that user can read, and in SYSTEM's temp folder (`wipe-local-data-*`) on Windows, which only SYSTEM and administrators can read. A run that finishes removes the mark. A home or profile that can't be marked, such as one whose data folder is reached through a link, is skipped. (A macOS home whose account no longer exists isn't marked, since no one can open the app there.) A file they can't remove is reported and the rest is still removed. Either way the script exits with an error so your MDM tool shows the device as failed. The Windows script looks only in `<profile>\AppData\Roaming`, so it can't reach AppData that Folder Redirection moved to a share; use `WipeLocalDataOnLaunch` there, which wipes only once that user opens OpenWhispr again, so for someone who won't, delete their data there by hand.

**macOS** (Jamf, Kandji or Intune, as root), [`scripts/mdm/wipe-local-data-macos.sh`](../scripts/mdm/wipe-local-data-macos.sh):

```bash
sudo ./wipe-local-data-macos.sh                       # every user, models kept
sudo ./wipe-local-data-macos.sh --include-models /Users/jdoe
```

In a Jamf Pro policy, put `--include-models` and the homes in parameters 4 and up, one per parameter; the script skips the three values Jamf passes first, and parameters left blank.

**Windows** (Intune, as SYSTEM), [`scripts/mdm/wipe-local-data-windows.ps1`](../scripts/mdm/wipe-local-data-windows.ps1):

```powershell
powershell -ExecutionPolicy Bypass -File .\wipe-local-data-windows.ps1
powershell -ExecutionPolicy Bypass -File .\wipe-local-data-windows.ps1 -IncludeModels -UserProfile C:\Users\jdoe
```

It needs Windows PowerShell 5.1, which Intune uses, in full language mode. Under PowerShell 7, or in the constrained language mode an AppLocker or WDAC policy can impose, it stops before removing anything. A note file that is a link or a cloud placeholder (OneDrive Files On-Demand) fails the run like one it can't read. OneDrive marks its folders the same way, so a notes folder in OneDrive fails every run and keeps the database: use `WipeLocalDataOnLaunch` there, which wipes only once that user opens OpenWhispr again, or delete the user's notes and data by hand. SYSTEM never goes through a junction or link a user made, not even to look, so one on the way to a folder the script cleans, such as a `.cache` moved to another drive with `mklink /J`, fails every run, whatever is behind it: check that folder by hand. So does an entry whose name ends in a dot or a space (a no-break space or U+0085 too), which Windows can take for another; a note in a folder named that way, the notes folder itself included, or one whose path is 260 characters or longer, which Windows PowerShell can't read, is reported and left, as one outside the profile, and the database still goes, so delete it by hand.

Tools that pass a script no arguments, such as Intune's scripts, run it with its defaults: every user, models kept. To take models there too, set `include_models=true` near the top of your copy of the macOS script, or give `$IncludeModels` a default of `$true` in the Windows one, and sign your edited Windows copy where a policy runs only signed scripts in full language mode.

Unlike the in-app wipe:

- The keychain item and temporary files (macOS) are removed only for the user signed in at the console. The Windows Credential Manager entry stays when the script runs as SYSTEM. With the encrypted files gone, those keys protect nothing.
- The Windows script also cleans the device-wide fallback folders (`%ProgramData%\OpenWhispr`, `C:\OpenWhispr`), even when you name profiles, and first. The app puts files there only when the user's temp or cache folder path has spaces or non-ASCII characters, which by default means the profile path has them, so while the script can't clean them, such a profile stays marked as unfinished.
- On macOS a user's files are removed as that user, so a link swapped in while the script runs can't reach anything they couldn't delete. On Windows each file and folder is deleted through a handle that shows it is where its path says, so a junction swapped in while the script runs can't send a delete elsewhere either. The Windows script still skips a profile whose user is signed in, since OpenWhispr may be running there, and, while any user is, a path Windows doesn't list for a user profile (such as `C:\Documents and Settings\jdoe`; name the profile as `C:\Users\jdoe`) and the shared `%ProgramData%\OpenWhispr` and `C:\OpenWhispr` folders, when they exist; it says so and exits with an error. If you deployed a `WipeLocalDataOnLaunch` token, the app wipes itself at its next launch; run the script again once the users have signed out. On macOS a root-owned folder in `/Users`, such as `/Users/Shared`, is skipped and reported, and the script exits with an error; a home whose account no longer exists is cleaned as root, from inside each folder so a link swapped in can't lead it out of the home, unless something still runs as that account, which skips it and fails the run. If macOS renamed the home when it deleted the account (`jdoe (Deleted)`), the notes it recorded under the old path are reported as outside the home: delete them by hand.
- Launch at login is left as it is; uninstall the app, or remove its login item with your MDM tool.

Neither the app nor the scripts remove the OpenWhispr CLI's own settings (`~/.openwhispr/cli-config.json`), which belong to the separately installed CLI. Revoke the account's API keys as part of offboarding.
