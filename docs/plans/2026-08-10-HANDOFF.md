## The bug, in one paragraph

Meeting detection silently stops working after a meeting. Ending a meeting
recording clears `_userRecording` but **not** `_meetingModeActive`
(`src/helpers/ipcHandlers.js:5845-5846`), and while that flag is true **every**
detection is dropped (`src/helpers/meetingDetectionEngine.js:245`). The only
thing that clears it in the whole renderer is the **"Back to notes"** button —
one call site, `src/components/ControlPanel.tsx:385`, rendered at `:750` behind
`isSidePanelLayout` (`:742`, defined `:88`). So detection dies after any meeting
where the user doesn't click that button. No crash needed. It looked random
because the trigger is a UI action, and it was invisible because file logging is
gated on debug mode rather than severity (`src/helpers/debugLogger.js:42`), so
the one `info` line it emits is never written to disk.

**User workaround until this ships:** click "Back to notes" after each meeting,
or restart the app.

## Stop signs

1. **Phase 3 (meeting identity) is DROPPED — user decision, 2026-08-11.** Not
   "pending redesign", not backlog. Do not implement it, and do not propose
   reviving that design. Adversarial review showed it would make things *worse*:
   at an id-change boundary both latches are still set and `call-active` is
   edge-triggered, so meeting B would get **no note at all** instead of a merged
   one. The goal (don't merge consecutive calls) stays valid — but if the symptom
   survives Phases 1–2, design fresh from telemetry.
2. **Phase 1a and 1b must ship in the same commit.** Always-persisting
   `warn`/`error` without rotation floods the disk —
   `src/helpers/deepgramStreaming.js:731-739` warns per audio chunk (~30/s) when
   `ws` is null, and renderer logs forward to the same file
   (`ipcHandlers.js:3505`).
3. **Guard `app?.isReady?.()` in debugLogger.** Under plain `node`,
   `require("electron")` returns a **string** and `app` is `undefined`
   (verified). Severity-gated file logging makes `debugLogger.js:54` reachable in
   tests → TypeError → suite dies.
4. **Do not kill the user's running app** while diagnosing. It has been up 4 d
   21 h and its state is the evidence.
5. **`better-sqlite3` ABI toggle.** `npm rebuild better-sqlite3` before tests;
   `npm run rebuild:native` before building the app. Mutually exclusive.
6. **Plan and review before coding** — `CLAUDE.md` → "Plan and Review Before
   Implementing". This plan has already had its fable review; act on the
   outcomes table rather than re-reviewing from scratch.

## What to implement

Phases 1, 2, 4 from the plan, with the review's required changes:

- **Phase 1** — severity-gated file logging + rotation (same commit),
  `meetingDetectionHealth.js` registry, a recorded reason at every suppression
  and failure path.
- **Phase 2** — the **lifecycle clear** of `_meetingModeActive` at
  `meeting-transcription-stop` (this is the actual bug fix); `try`/`catch` on the
  three set-then-await paths; short watchdog backstop (~10–15 min after
  `_userRecording` drops, **not** hours); supervision + restart for **both**
  native children incl. `macos-call-detector` (`callStateDetector.js:70-77` has
  no restart and doesn't reset state); `hasPrompted` absolute max age;
  `activeDetections` TTL; resume-from-sleep revalidation; make the dead macOS
  polling fallback declare itself `unavailable` rather than pretend to poll.
- **Phase 4** — health IPC + preload + types, Settings status row
  (Healthy/Degraded/Unavailable + reason + "Open logs", reusing
  `open-logs-folder` at `ipcHandlers.js:6461` / `preload.js:544`), a one-time
  notice when detection can't run, i18n keys in **all 10 locales**.

Suggested sequencing: **land the lifecycle clear first as its own small commit**
so the user gets working detection immediately, then the telemetry build.
