# keyboard-extension (Expo config plugin + iOS extension target)

A custom iOS keyboard extension that lets the user dictate from any text field system-wide. Its keys look and type like Apple's keyboard; the toolbar above them holds the options button, the dictation pill and the agent button, and while a word is typed the pill makes room for three suggestions. Typing help (autocorrect, suggestions, swipe typing, learned words, emoji) runs on the device in English and German; see [Typing](#typing). The options button opens a menu for tone, for translating dictation, and a link to the app's keyboard settings; see [Translation](#translation). The pill always reads **Tap to speak**. A tap records in place through the OpenWhispr app's background session, or in the keyboard itself (see Handoff below for when); only when neither can take the dictation does the same tap open the app and hand off to it.

## How it works

1. User installs the keyboard from iOS Settings → General → Keyboard → Keyboards → Add New, and turns on Allow Full Access.
2. User opens any app, switches to the OpenWhispr keyboard and taps the pill.
3. **In place.** When the app's background session is ready (`isBackgroundSessionReady()`), or when the keyboard is inside OpenWhispr itself, the pill reads **Tap to speak**. A tap writes a start request to the App Group and posts a Darwin notification. The app records without leaving the host app, the keyboard shows a recording canvas, and it inserts the transcript when `transcriptReady` arrives.
4. **In the keyboard (iOS 26+).** When the app isn't running and Preferences → Keyboard → **Dictate without opening OpenWhispr** is on, a signed-in OpenWhispr Cloud user's tap records in the keyboard itself: a hidden `WKWebView` holds the microphone (`WebAudioCapture.swift`; a keyboard extension is refused native recording), the take is boosted, encoded as AAC and sent to `/api/transcribe` with the session the app shares through the App Group keychain (`DirectDictation.swift`, `DirectDictationRuntime.swift`). A Local Mode user on Parakeet dictates in the keyboard too: the take never leaves the phone, and the keyboard types the transcript without cleanup (a custom cleanup prompt keeps the handoff). `KeyboardParakeetTranscriber.swift` loads the model the app downloaded into the App Group onto the Neural Engine with FluidAudio (never the GPU, never a download; it keeps a model only once it's on the Neural Engine and while the keyboard has room for it), starts loading when the keyboard appears, and lets go of it on a memory warning once no transcription needs it. Until the model is ready, a tap hands off to the app. The app's snapshot (`keyboard_direct_config`, written by `src/lib/keyboardDirectSync.ts`) decides when this is allowed; Bring Your Own Key, Whisper in Local Mode, a custom cleanup prompt, guests, the assistant, and dictating while other audio plays or over Bluetooth keep the handoff, as does a selected translation language the snapshot cannot translate (for a Local take, any language but the dictation language itself, since translating is a network request). Each dictation leaves a record in the App Group's `direct-dictations/` folder, which the app turns into History (`src/lib/keyboardDirectOutbox.ts`). Its Swift tests run with `npm run test:keyboard-direct`.
5. **Handoff.** Only when neither of those applies does the tap open the app. The pill still reads **Tap to speak** (it read **Activate** before, which looked like a different state for something the user can't act on); a link over the pill opens `<scheme>://keyboard-dictation` (handled by [src/hooks/useKeyboardHandoff.ts](../../src/hooks/useKeyboardHandoff.ts)). The app starts a native recording, then sends the user back to the host app (`returnToHost` in [src/lib/handoffReturn.ts](../../src/lib/handoffReturn.ts)). iOS 26.4+ hides the host from the extension, so the containing app learns it from UIKit ([`HostAppObserver.swift`](../../modules/app-group-storage/ios/HostAppObserver.swift)). When no host is found, the app shows the "Swipe back to your app" screen instead. The transcript is pasted on the keyboard's next focus.

## Typing

Everything here runs on the device. Keystrokes and typing history never leave the phone or reach the logs, and learned words stay in the App Group container. Without Full Access none of it loads and the keyboard types plainly.

- **Languages and layouts.** English and German, QWERTY and QWERTZ (German has umlaut keys on either). The app's Preferences → Keyboard typing sets both; a long press on the emoji key switches them from the keyboard. Stored in the App Group (`keyboard_typing_language`, `keyboard_typing_layout`); unset, they follow the device's preferred languages, and typing help is on only when one of them is English or German. A third language choice, "Other (no typing help)" (`keyboard_typing_language` = `other`), is for languages without a word list: suggestions, autocorrect, swipe and smart key targets are off, and the keys, haptics and trackpad stay. "Français (Suisse)" (`fr_CH`) is the same without typing help, with è, é and à on keys of their own where German has its umlauts (QWERTZ unless a layout is chosen).
- **Autocorrect and suggestions.** `TypingSession` follows the text and answers each key with the edit to make; `Autocorrector` scores candidates from the bundled lexicon (word and word-pair frequencies), learned words and iOS's supplementary lexicon (text replacements, contact names). A correction is made at a word boundary and backspace takes it back. Fields that ask for none get none: autocorrection or spell checking off, URL and email keyboards, user names, passwords, one-time codes, and fields that hide their text (which are never learned from).
- **Suggestion bar.** Two layouts behind `keyboard_suggestion_bar_style`: `strip` (default) shows the suggestions between the options and assistant buttons while a word is typed, with dictation as a 44 pt mic button; `row` adds a suggestion row above the toolbar. `TypingSettings.defaultBarStyle` picks the default.
- **Swipe typing**, **dynamic hit targets** (the touch boundary between letters leans toward the likelier next letter; the inner 60% of a key always types it), **space-bar trackpad**, **long-press accents**, a **number pad** for number fields, **haptics** (a light tap per key; `keyboard_haptics_enabled`), and an **emoji panel** with search, skin tones and Recents.
- **Benchmarks.** `tests/benchmarks/` holds the frozen datasets (see its README); `sh scripts/test-keyboard-typing.sh autocorrect|swipe|targets …` runs them, and with no arguments runs the engines' unit tests. Tune on `dev`, report on `test`.

## Translation

The options button (`slider.horizontal.3`, `optionsButton` in `KeyboardViewController.swift`) shows the language code, for example `ES`, while a target language is selected. Its menu holds Tone, Translate to (Off, recent languages, All languages) and Keyboard Settings…, which opens `<scheme>://keyboard-settings` in the app at Preferences (`src/lib/keyboardSettingsLink.ts` keeps a warm resume from replacing it with Home). The same choice is under Preferences → Translate dictation (`src/screens/KeyboardTranslationScreen.tsx`). The menu is rebuilt each time it opens, so it and the badge follow changes the app made while the keyboard was showing. An over-the-air update running on a build from before translation (no `getSupportedLanguages` in `modules/apple-llm`) keeps translation off and hides the Preferences row, since that keyboard can't show or turn off a language.

- **Languages.** Cloud and Bring Your Own Key offer the registry list. On-Device offers only what Apple Intelligence reports (`getSupportedLanguages` in `modules/apple-llm`), and translation isn't available there while Apple Intelligence can't run (turned off, still downloading, or not on this iPhone). A selected language the current route can't translate into is kept and shows as Off, so it is back when the route is (the route can also read as On-Device for a moment, in Local Mode before sign-in is restored). Until the app marks translation as available (`keyboard_translation_applicable`), the submenu reads **Set up translation in OpenWhispr**, with every language locked and Off still usable.
- **App Group keys.** `keyboard_translation_target` is the source of truth (absent means Off); the keyboard and the app both write it. `keyboard_translation_languages` and `keyboard_translation_applicable` are written by the app (`src/lib/keyboardTranslationSync.ts`), `keyboard_translation_recents` by the keyboard. `keyboard_recording_translation` and `keyboard_recording_translation_job_id` snapshot the effective target per job (Off when translation isn't available or the stored language isn't listed), so a change mid-recording does not affect it.
- **In the app.** `src/lib/transcribeAndCleanup.ts` transcribes, cleans up, expands snippets, then translates (`src/lib/translateTranscript.ts`) on the job's pinned cleanup route with the shared translate prompt. If translation fails, the untranslated text is typed with a warning, added after any cleanup warning. A cancelled dictation ends its translate request and never retries it. On-Device, a reply that reaches Apple Intelligence's output limit counts as cut off and fails (detectable from iOS 26.4, which counts tokens). Only a dictation language that is exactly the target skips the step (as desktop); the dictation language carries no region, so a regional target such as English (UK) or Chinese (Traditional) is always sent, and a reply identical to the text is typed without a warning. History keeps the raw transcript as `originalText` and records `translatedTo`; a failed row keeps the target in `translationTarget`, so its retry translates. When the app was killed during a keyboard upload, its orphan recovery translates too. The native uploader keeps text the server already cleaned (fused cleanup) for it when a target was snapshotted for the job, marked by `keyboard_orphaned_transcript_cleaned_job_id`, so it isn't cleaned twice.
- **In the keyboard (app closed).** `keyboard_direct_config` carries `translation: { enabled, prompt }`. It is true only when direct dictation is enabled, translation applies to the route (`translationApplies`), and the cleanup route is OpenWhispr Cloud (`cleanupMode === 'openwhispr'`), since the keyboard translates through `/api/reason` only. A Local snapshot (`engine: "local"`) always carries it off, Local Mode with Cloud cleanup included, since a Local take never reaches the network; the keyboard also refuses to give a Local take a target or build a translate request for one whatever the snapshot says, so with a language selected a Local take goes to the app, which translates on its own route. The order is the app's: cleanup, snippet expansion, then one extra `/api/reason` request for the translation (`DirectDictationRequests.swift`). It carries `x-openwhispr-client-timeout-ms` like the app's. That request is not retried; a failed or refused one types the expanded, cleaned text untranslated and records `translationFailed`, which becomes the History row's warning (an unchanged reply is not a failure). For a new take, the keyboard records by itself only when no language is selected, `translation.enabled` is true, or the target is exactly the dictation language. With another language selected and `translation.enabled` false, direct dictation stands down and the take goes through the in-place or handoff route, where the app translates on the user's own route. A take already in flight or being recovered is not affected.

## Apple capabilities required

- **App Group** (`group.<ios bundle id>`) — must match between the main app, the extension, and the `app-group-storage` module. The app keeps its Parakeet models there too, at `Library/Application Support/SpeechModels/<folder>` (`parakeet-tdt-0.6b-v2`, `parakeet-tdt-0.6b-v3`, the folder names FluidAudio loads from; see [`modules/parakeet-asr/ios/SharedSpeechModels.swift`](../../modules/parakeet-asr/ios/SharedSpeechModels.swift)), excluded from backup and moved there from the app's own container by builds that predate it.
- **Open Access** (`RequestsOpenAccess` in `Info.plist`) — required for the extension to read/write the shared suite.

## Environments

Runtime identifiers are resolved from `config/openwhispr-environments.js` and applied by `app.config.js` plus this plugin during prebuild.

- Production/TestFlight: `OPENWHISPR_APP_ENV=production`
- Development: `OPENWHISPR_APP_ENV=development`
- Local signing override: set `OPENWHISPR_IOS_BUNDLE_IDENTIFIER` and `OPENWHISPR_SCHEME` when needed. The App Group defaults to `group.<OPENWHISPR_IOS_BUNDLE_IDENTIFIER>`.

Verify with:

```bash
OPENWHISPR_APP_ENV=development npx expo config --json
```

After changes, regenerate the native project:

```bash
OPENWHISPR_APP_ENV=development npx expo prebuild --clean
npm run ios
```

## Simulator harness

`python3 plugins/keyboard-extension/tests/run-keyboard-sim-harness.py <simulator udid> --tests | --perf | --screenshots <dir> --device <se|promax>` builds the production keyboard sources and the tests as a small app (plain `swiftc`, no Expo build), runs it in the simulator and prints the result: the typing checks on a real iOS, latency and memory figures, and screenshots in true light and dark. `tools/compose-keyboard-comparisons.py` stacks those screenshots under Apple's reference shots.

## Keyboard touch regression tests

On macOS with Xcode:

```bash
python3 openwhispr-mobile/plugins/keyboard-extension/tests/run-keyboard-touch-tests.py
```

Run it from the repository root after changing the keyboard layout, its padding or key targets; mobile CI runs it too. The runner compiles the production keyboard Swift sources for Mac Catalyst, so it needs no simulator, signing credentials or Expo build; it stubs what iOS would tell the keyboard (the field behind it, the globe key, a phone or an iPad, landscape). It tests UIKit hit routing across row gaps, overlapping key targets, unequal key widths, nested stacks, hidden layouts, disabled keys and keyboard boundaries, then lays out the real keyboard at every iPhone width in portrait and landscape, on all three pages, with and without the globe key, on iPad, and with the URL, email, web search and Twitter bottom rows and a greyed return key, and checks that no tap below the dictation strip is dropped, the keyboard's padding included. It also checks shift after letters and deletes, smart quotes per field, the return key and Twitter rows per page, rotation, the globe key settling late, a view shorter than the keyboard, and the review card's extra height.

These touch tests do not measure typing latency. Before releasing,
check fast two-thumb typing and repeated letters on an iPhone, near-edge taps,
Shift, 123/ABC, space/return, held delete, keyboard switching, and dictation in
portrait and landscape in Notes and another host app.
